## 1. Цель и контекст

Построить в веб-панели Iceberg модуль **«Бухгалтерия» / «Финансы»**, в котором суперадмин и уполномоченные администраторы контролируют:

- проданные товары: онлайн-заказы, фургоны, прямые продажи со склада;
- новые поставки, документы накладных и их себестоимость;
- остатки и все движения товара;
- выручку, себестоимость, валовую прибыль и управленческие расходы;
- оплаты, возвраты оплат и расхождения между продажами и денежными поступлениями;
- статистику складов, сотрудников и водителей;
- ручные корректировки и действия пользователей;
- качество и полноту финансовых данных.

Ключевой принцип:

> **Данные финансового модуля появляются из операционных событий и первичных документов.**

Заказ доставлен → создаётся продажа.

Поставка принята → создаётся документ поставки и движение прихода.

Продажа возвращена → создаётся корректирующее событие/сторно.

Склад пересчитан → создаётся документ инвентаризации и корректировка.

Товар списан → создаётся движение `WRITE_OFF`.

Товар перемещён → создаётся `TRANSFER_OUT` и связанный `TRANSFER_IN`.

Суперадмин не должен вручную вводить продажу или произвольно менять историю операций. Ручной ввод разрешён только для специальных первичных документов и корректировок с обязательным аудитом.

### 1.2 Ключевые разрывы, которые закрывает спецификация

1. Нет единого управленческого P&L.
2. Нет полноценного документа поставки с заголовком, строками, складом, поставщиком и аудитом проведения.
3. Нет единой модели корректировок и сторно для финансовых событий.
4. Нет полноценного аудита критичных действий.
5. Нет инвентаризационного документа.
6. Нет межскладских перемещений как отдельного типа движения.
7. Нет единого контроля качества данных и финансовых расхождений.
8. Нет стабильного API кросс-складовых отчётов.
9. Нет финансового UI для sales ledger, supplies, movements, KPI и control center.
10. Нет готовой модели для последующего перехода от текущей стоимости остатка к weighted average / FIFO.

## 3. Термины и границы модуля

### 3.1 Управленческий учёт

Модуль рассчитывает управленческие показатели на основании операционных данных и документов.

Он отвечает на вопросы:

- сколько продали;
- сколько товара продали;
- сколько это стоило по принятому в MVP методу оценки;
- сколько денег получили;
- сколько товара закупили;
- сколько товара вернули/списали;
- где возникают расхождения;
- что происходит со складами и персоналом.

### 3.2 Источник правды

Для каждого типа данных определяется один первичный источник:

| Данные | Источник |
|---|---|
| Продажи | `WarehouseSale` и связанные корректировки |
| Заказы | `Order` / `OrderItem` |
| Оплаты | `Payment` |
| Поставки | `SupplyDocument` / `SupplyDocumentLine` |
| Текущий остаток | `ProductStock` |
| История движений | `StockHistory` |
| Инвентаризации | `InventoryCount` |
| Возвраты | `ProductReturn` + связанные adjustment events |
| Вознаграждения | `EmployeeReward` |
| Действия пользователей | `AuditLog` |

Accounting API не должен создавать конкурирующую историю тех же событий.

## 4. Роли и права

Два независимых слоя. Их нельзя смешивать в один флаг.

1. **Permission** — глобальная способность (видеть прибыль, проводить документ, экспортировать).
2. **Warehouse scope** — какие склады видны в выборках. Считается отдельно, после проверки permission.

| Роль / профиль | Warehouse scope | Permission-профиль |
|---|---|---|
| Суперадмин (`isSuperAdmin`) | Все склады | `FULL` |
| ADMIN без доп. профиля | Все склады (как сейчас в warehouse/admin API) | `OPERATOR` |
| ADMIN с `accountingProfile = FINANCIER` | Все склады | `FINANCIER` |
| EMPLOYEE | Только `employee.warehouseId` + `employee.warehouses` | `OPERATOR` в пределах scope, без profit/cost |
| SUPPLIER | Нет accounting | — |
| DRIVER / CLIENT | Нет accounting | — |

`FINANCIER` — управленческий финансист: видит COGS, прибыль и P&L, может экспортировать и смотреть аудит, **не** проводит/сторнирует документы, **не** меняет остатки, **не** управляет пользователями. В MVP это поле на `Admin`, не новая `UserRole`.

```text
Admin.accountingProfile = OPERATOR | FINANCIER | FULL
FULL ⇔ isSuperAdmin
по умолчанию у обычного ADMIN = OPERATOR
```

### 4.1 Permission-контракт

Permission — глобальные флаги. Warehouse scope к ним не пришивается.

| Permission | OPERATOR | FINANCIER | FULL |
|---|---|---|---|
| `ACCOUNTING_VIEW` | да | да | да |
| `ACCOUNTING_REVENUE_VIEW` | да | да | да |
| `ACCOUNTING_COST_VIEW` | нет | да | да |
| `ACCOUNTING_PROFIT_VIEW` | нет | да | да |
| `ACCOUNTING_SUPPLY_CREATE` | да | нет | да |
| `ACCOUNTING_SUPPLY_RECEIVE` | да | нет | да |
| `ACCOUNTING_SUPPLY_REVERSE` | нет | нет | да |
| `ACCOUNTING_STOCK_ADJUST` | нет | нет | да |
| `ACCOUNTING_INVENTORY_CREATE` | да | нет | да |
| `ACCOUNTING_INVENTORY_COMPLETE` | да | нет | да |
| `ACCOUNTING_TRANSFER_CREATE` | нет | нет | да |
| `ACCOUNTING_AUDIT_VIEW` | нет | да | да |
| `ACCOUNTING_EXPORT` | да, без cost/profit | да, полный | да |
| `ACCOUNTING_LATE_ENTRY` | нет | нет | да |
| `ACCOUNTING_PERIOD_CLOSE` | нет | нет | да |
| `ACCOUNTING_CASH_CONTROL` | нет | да (чтение) | да |

На первом этапе таблица `Permission` не обязательна: флаги вычисляются из `isSuperAdmin` + `Admin.accountingProfile`. Сервер режет DTO по permission **до** сериализации ответа. Warehouse scope применяется как `WHERE warehouseId IN (...)`.

Правило: «в пределах доступных складов» относится только к scope-фильтру, а не к имени permission.

### 4.2 EMPLOYEE и инвентаризация (осознанное упрощение v2.1+)

Формулировка v2.0 «сотрудник участвует в инвентаризации после выдачи права» **снята**.

В MVP:

- профиль EMPLOYEE = `OPERATOR` без cost/profit;
- `ACCOUNTING_INVENTORY_CREATE` и `ACCOUNTING_INVENTORY_COMPLETE` у OPERATOR включены **по умолчанию**;
- ограничение — только warehouse scope: свой `warehouseId` и `warehouses`, не чужие склады;
- отдельной выдачи permission, отдельного флага на Employee и отдельного экрана «назначить инвентаризатора» нет.

Это упрощение, не пробел. Если в эксплуатации понадобится «кладовщик принимает поставки, но не закрывает инвентаризацию» — это V2 и отдельный permission, не блокер M1.

ADMIN с профилем OPERATOR инвентаризирует все склады компании.

## 5. Источник правды и финансовые инварианты

### 5.1 Продажи

Продажа появляется только через существующий операционный flow:

- `WarehouseSaleService.createSalesFromOrder`
- `WarehouseSaleService.createSalesFromStop`
- `WarehouseSaleService.createDirectSale`

Accounting не создаёт продажи.

### 5.2 Историчность

После появления продажи в ней должны быть зафиксированы исторические значения, необходимые для отчётов:

- `salePriceAtSale`;
- `costAtSale` / `warehousePriceAtSale`;
- `isEstimatedCost`;
- `profitAtSale`;
- `soldAt`;
- идентификаторы склада и товара;
- исходный документ/событие.

Историческая себестоимость продажи **никогда не должна пересчитываться через текущий `ProductStock.warehousePrice`**.

### 5.3 Денежная точность

Все новые денежные поля в Prisma:

```prisma
Decimal @db.Decimal(12, 2)
```

Не добавлять новые финансовые поля типа `Float`.

Для существующих `Float`-полей допускается использование безопасных Decimal-конвертаций в accounting service без массовой миграции старой схемы в рамках этого релиза.

### 5.4 Денормализованные суммы

Например `SupplyDocument.totalAmount` может использоваться для быстрого отображения, но не является источником правды.

Источник:

```text
SUM(line.quantity × line.unitCost)
```

После изменения строк сумма должна пересчитываться или валидироваться.

### 5.5 Алгоритм себестоимости MVP (`CURRENT_STOCK_PRICE`)

Это **не** метод оценки запасов (не FIFO и не средняя). Это правило «на остатке хранится последняя известная явная закупочная цена; в продажу копируется снимок этой цены».

Обозначения:

- `ProductStock.warehousePrice` — текущая явная закупочная цена коробки на складе. Может быть `null`.
- `SupplyDocumentLine.unitCost` — цена закупки в строке накладной. Опциональна.
- `costAtSale` — снимок себестоимости в момент продажи. Иммутабелен.

#### Приход (`RECEIVED`)

Для каждой строки в одной транзакции с `addSupply`:

| `unitCost` в строке | Что происходит с `ProductStock.warehousePrice` |
|---|---|
| задан (не null) | **Заменяется** на `unitCost` этой строки. Предыдущая цена остатка не усредняется. |
| пуст | **Не меняется.** Старая явная цена остаётся. Не обнуляется. |

Если на складе не было строки `ProductStock` и `unitCost` пуст: создаётся остаток с `warehousePrice = null`.

Две поставки подряд до продажи:

```text
приход 10 × 80 ₽  → warehousePrice = 80
приход 5  × 100 ₽ → warehousePrice = 100
продажа 3 коробки → costAtSale = 100 (последняя явная цена на момент продажи)
```

Это намеренно «last explicit cost», не средневзвешенная. При переходе на `WEIGHTED_AVERAGE` исторические `costAtSale` не пересчитываются; меняется только правило записи `warehousePrice` / расчёта новых продаж.

#### Продажа

```text
explicitCost = ProductStock.warehousePrice        // может быть null
costAtSale   = explicitCost
               ?? PriceCalculationService.getEffectiveWarehousePrice(...)
isEstimatedCost = (explicitCost == null)
```

`costAtSale` и `isEstimatedCost` пишутся в продажу и больше не читаются с текущего остатка.

#### Постфактумная правка цены остатка

Отдельная операция `PRICE_CHANGE`, не побочный эффект правки накладной:

- право: только `FULL` (`ACCOUNTING_COST_VIEW` недостаточно);
- обязательный `reason`;
- `AuditLog` + запись в `StockHistory.data` (quantity=0 допустим, это не движение товара);
- **не** меняет `costAtSale` уже существующих продаж;
- новые продажи идут по новой цене.

Нельзя «дописать» `unitCost` в уже `RECEIVED` строку. Исправление: reversal (если проходит проверку остатка) + новый документ, либо `PRICE_CHANGE` только для будущих продаж.

#### Пустой `unitCost` и качество данных

Строки без `unitCost` после `RECEIVED` попадают в Control Center («поставки без unitCost»). Продажи с `isEstimatedCost=true` попадают в `cogs.estimated`.

### 5.6 Отрицательные остатки запрещены

Бизнес-решение, не рекомендация.

`ProductStock.quantity >= reserved >= 0` всегда. `available = quantity - reserved >= 0`.

Любая операция, которая уменьшает остаток (`SELL`, `WRITE_OFF`, `TRANSFER_OUT`, `SUPPLY_REVERSAL`, `SUPPLY_RETURN`, отрицательный `ADJUSTMENT`), **блокируется**, если `available < amount`:

```text
400/409: недостаточно доступного товара
```

Это уже делает `InventoryService.decrementAvailable` и `setQuantity` (отказ от `quantity < 0` и `quantity < reserved`). Accounting не имеет права обойти эти проверки.

Следствия:

- продажа в минус не создаётся;
- сторно поставки не уводит склад в минус;
- инвентаризация не может установить количество ниже `reserved`.

Пункт Control Center «отрицательные остатки» — детектор **аномалии** (легаси, баг, гонка). Это не разрешённое состояние. При обнаружении:

1. алерт суперадмину (§16.2);
2. ручная инвентаризация / расследование;
3. нельзя «нормализовать» минус новой продажей.

### 5.7 Конкурентный доступ к `ProductStock`

Все мутации остатка — только через `InventoryService` внутри Prisma transaction.

Обязательный протокол на одну строку `(productId, warehouseId)`:

1. Открыть транзакцию.
2. Заблокировать строку `ProductStock`: `SELECT ... FOR UPDATE` (через `$queryRaw` / эквивалент). Если строки нет — создать и заблокировать повторно.
3. Перечитать `quantity` и `reserved`.
4. Применить бизнес-проверку `available`.
5. Изменить остаток **условным** `updateMany` с предикатом на ожидаемые `quantity`/`reserved` (уже есть в `setQuantity` / `decrementAvailable`).
6. Если `count = 0` → `409 Conflict`, клиент повторяет.
7. Писать `StockHistory` только после успешного update.

Дополнительно в MVP добавить `ProductStock.version Int @default(0)` и инкремент в том же `UPDATE`. Устаревшая версия = `409`.

Изоляции `SERIALIZABLE` на всю БД не требуется: достаточно row lock + optimistic predicate. Несколько разных SKU на одном складе могут идти параллельно.

Write-операции accounting (`receive`, `reverse`, `inventory complete`, `transfer complete`, `adjustment`) обязаны использовать этот протокол, а не свой SQL к `ProductStock`.

### 5.7.1 Порядок блокировок (несколько строк в одной транзакции)

Протокол §5.7 описан для одной строки. В одной транзакции часто блокируется несколько `ProductStock`:

| Операция | Какие строки |
|---|---|
| `TRANSFER` complete | источник и получатель: два `(warehouseId, productId)`, часто один SKU на двух складах |
| `SupplyDocument` receive / reverse | все строки документа на одном складе: много `productId` |
| `InventoryCount` complete | все строки пересчёта |
| пакетный adjustment | несколько SKU |

Если два запроса блокируют пересекающееся множество в разном порядке (`A→B` и `B→A`), возможен deadlock.

**Обязательное правило:** перед любым `FOR UPDATE` собрать ключи, отсортировать и блокировать только в этом порядке:

```text
ORDER BY warehouseId ASC, productId ASC
```

Следствия:

- transfer A→B и transfer B→A оба сначала берут меньший `warehouseId`;
- два receive с пересекающимся набором SKU идут в одном порядке productId;
- недостающую строку сначала **создают** (в том же порядке ключей), затем блокируют повторным `SELECT ... FOR UPDATE`;
- запрещено блокировать «сначала источник, потом получатель», если получатель сортируется раньше источника.

На deadlock Postgres (`40P01`) транзакция откатывается; клиент может повторить с тем же `Idempotency-Key`. Это запасной путь, не замена ordered lock.

Тест: два параллельных transfer встречных складов не зависают и не оставляют рассинхрон остатков (AC-21).

### 5.8 Товарный возврат и возврат денег — независимые события

| Событие | Источник | Деньги | Товар |
|---|---|---|---|
| Физический возврат на склад / поставщику | `ProductReturn` + stock movement `RETURN` / `SUPPLY_RETURN` | нет автоматически | да |
| Возврат оплаты | `Payment` status `REFUNDED` / `refundAmount` | да | нет автоматически |
| Корректировка продажи в отчёте | `SalesAdjustment` | по сумме adjustment | по qty adjustment |

Они **не** связаны 1:1. Допустимы:

- товар вернули, деньги не вернули (порча по вине клиента, замена);
- деньги вернули, товар не вернулся (порча в доставке, недовоз);
- оба события по одному заказу, но в разное время и на разные суммы/qty.

Опциональная ссылка, не обязательный FK:

```text
SalesAdjustment.paymentId?
ProductReturn.orderId? / paymentId?
```

Ни один сервис не создаёт платёжный refund из `ProductReturn` и не создаёт складское движение из webhook ЮKassa. Control Center показывает непарные случаи как расхождения, не как ошибку проводки.

## 6. Выручка, оплата и P&L

### 6.1 Товарная выручка

```text
Revenue = SUM(WarehouseSale.salePriceAtSale × quantity)
```

по `soldAt` за выбранный период.

Разрезы:

- `ORDER`;
- `STOP`;
- `DIRECT`.

### 6.2 Доход от доставки

`Order.deliveryFee` учитывается отдельно.

Для заказа со статусом `DELIVERED`:

```text
DeliveryRevenue = deliveryFee
```

Если доставка бесплатная — 0.

### 6.3 Оплаты

Показывать отдельно:

- `COMPLETED`;
- возвраты/`REFUNDED`;
- net payments.

Не считать `Order.totalAmount` автоматически денежным поступлением.

### 6.4 Расхождение

Основной контроль:

```text
ExpectedRevenue = ProductRevenue + DeliveryRevenue
PaymentNet = CompletedPayments - Refunds
Difference = ExpectedRevenue - PaymentNet
```

Расхождение не должно искусственно «исправляться» в accounting. Оно должно быть отображено и классифицировано.

### 6.5 COGS

```text
COGS = costAtSale × quantity
GrossProfit = Revenue - COGS
GrossMargin = GrossProfit / Revenue × 100  // при Revenue = 0 маржа не считается, в API null
```

`costAtSale` берётся только из снимка продажи. Алгоритм, как этот снимок появился, — §5.5.

Если `isEstimatedCost = true`, сумма идёт в `cogs.estimated`, иначе в `cogs.actual`. Оба входят в `cogs.total`.

### 6.6 Методы оценки себестоимости

В модели предусматривается код метода на будущее:

```text
CURRENT_STOCK_PRICE   // MVP, алгоритм §5.5: last explicit cost на остатке + снимок в продаже
WEIGHTED_AVERAGE      // V3
FIFO                  // V3
```

Поле `costingMethod` хранится в настройках компании, в MVP константа `CURRENT_STOCK_PRICE`. Смена метода не пересчитывает уже записанные `costAtSale` и не меняет `warehousePrice` задним числом.

### 6.7 Операционный P&L

MVP:

```text
GrossProfit
- completed product returns / sales adjustments
- paid employee rewards
- write-offs / other approved operational expenses where applicable
= Operating Result
```

При этом **закупки не вычитаются из COGS второй раз**.

Отдельно показывается:

```text
SupplySpend = SUM(received supply lines)
```

как движение стоимости запасов / cash outflow, а не как повторный расход P&L.

## 7. Возвраты, сторно и корректировки

Это обязательная часть финансовой модели.

### 7.1 Возврат проданного товара

После `DELIVERED` продажа не удаляется и её историческая стоимость не меняется.

Возврат создаёт отдельное корректирующее событие, связанное с исходной продажей.

Варианты реализации:

```text
SalesAdjustment
```

или специализированная сущность, если текущая модель возвратов уже полностью покрывает связь.

Для каждого возврата должны быть доступны:

- `sourceSaleId`;
- `productId`;
- `warehouseId`;
- quantity;
- amount;
- cost;
- reason;
- createdAt;
- createdById.

Связь с возвратом денег — опциональна. Жёсткой пары «товарный возврат = refund Payment» нет (§5.8).

### 7.2 Частичный возврат

Поддерживается:

```text
Sold: 10
Returned: 2
Net sold: 8
```

Нельзя создавать отрицательное количество, превышающее исторически проданное.

### 7.3 Продажа после возврата

Историческая запись `WarehouseSale` остаётся неизменной.

Расчёт отчёта:

```text
Gross Sales
- Sales Adjustments
= Net Sales
```

### 7.4 Возвраты поставщику

Товар, возвращённый поставщику, не должен уничтожать исходный документ поставки. Для этого в модели движений зарезервирован тип `SUPPLY_RETURN`.

**В MVP операция не создаётся.** Нет сервиса, нет endpoint, нет permission `ACCOUNTING_SUPPLY_RETURN`, нет UI. Значение enum в `StockHistory.operation` можно добавить заранее, чтобы не плодить миграцию в V2, но write-path, который пишет `SUPPLY_RETURN`, в MVP отсутствует.

Существующий `ProductReturn` (застоявшийся товар, `productReturn.controller`) остаётся операционным контуром как есть. Он не является документом `SUPPLY_RETURN` и не сторнирует `SupplyDocument`.

В V2: документ возврата поставщику, permission `ACCOUNTING_SUPPLY_RETURN` (FULL), UI, связь с исходной строкой поставки, проверка `available` как в §8.7.

Исходный приход всегда остаётся аудируемым. Сторно поставки в MVP — только `SUPPLY_REVERSAL` (§8.7), не `SUPPLY_RETURN`.

## 8. Поставки

### 8.1 SupplyDocument

Предлагаемая модель:

```prisma
model SupplyDocument {
  id             Int      @id @default(autoincrement())
  number         String
  supplierId     Int
  warehouseId    Int
  status         SupplyDocumentStatus @default(DRAFT)
  documentDate   DateTime
  receivedAt     DateTime?
  receivedById   Int?
  reversedAt     DateTime?
  reversedById   Int?
  cancelledAt    DateTime?
  cancelledById  Int?
  comment        String?
  totalAmount    Decimal  @default(0) @db.Decimal(12,2)
  isLateEntry    Boolean  @default(false)
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  supplier       Supplier @relation(...)
  warehouse      Warehouse @relation(...)
  lines          SupplyDocumentLine[]
}
```

### 8.2 Статусы

Базовые:

```text
DRAFT
RECEIVED
CANCELLED
REVERSED
```

Опционально для будущего partial receiving:

```text
PARTIALLY_RECEIVED
```

### 8.3 SupplyDocumentLine

```prisma
model SupplyDocumentLine {
  id              Int      @id @default(autoincrement())
  documentId      Int
  productId       Int
  quantity        Int
  unitCost        Decimal? @db.Decimal(12,2)
  barcodeScanned  String?
  product         Product @relation(...)
  document        SupplyDocument @relation(...)
}
```

### 8.4 Номер документа

Поддерживаются:

- номер накладной поставщика;
- внутренний номер, если внешнего номера нет.

Уникальность номера должна учитывать поставщика или иной бизнес-ключ.

### 8.5 Проведение

При `RECEIVED` в одной Prisma transaction:

1. Проверить `DRAFT`/разрешённый промежуточный статус.
2. Проверить минимум одну строку.
3. Проверить активность склада.
4. Проверить существование товаров.
5. Проверить права пользователя.
6. Проверить соответствие supplier/product relationship.
7. Проверить период: `documentDate` не в закрытом периоде без `ACCOUNTING_LATE_ENTRY`; не в будущем (§8.9, §17.1).
8. Применить `InventoryService.addSupply` по протоколу §5.7.
9. Создать `StockHistory(operation=SUPPLY)` с `sourceType=SUPPLY`, `sourceId=supplyDocumentId`.
10. Обновить `ProductStock.warehousePrice` строго по таблице §5.5 (пустой `unitCost` не обнуляет цену).
11. Перевести документ в `RECEIVED`.
12. Записать `receivedAt`, `receivedById`.
13. Если `documentDate` в закрытом периоде и есть право late entry — `isLateEntry=true`.
14. Создать `AuditLog`.
15. Инвалидировать продуктовый и складской кеш.

Повторное проведение того же документа без нового idempotency-key → `409 Conflict` (§28.3).

### 8.6 Отмена DRAFT

`DRAFT → CANCELLED` не изменяет остаток.

### 8.7 Сторно RECEIVED

Проведённую поставку нельзя физически удалить.

Для неё создаётся reversal:

```text
SUPPLY +100
SUPPLY_REVERSAL -100
```

Не допускается превращать исторический документ в «будто его не было».

#### Ограничение MVP: партий нет

Система **не знает**, лежат ли на складе именно коробки этой поставки. Есть только агрегат `ProductStock.quantity` / `reserved`.

Единственная допустимая проверка:

```text
available = quantity - reserved
если reverseQty > available → отказ, сторно не проводится
```

Это **прокси «на складе достаточно коробок»**, а не доказательство «эта поставка ещё не продана». Формулировка «товар уже частично продан, полное сторно не разрешается» в реализации означает только эту проверку остатка, без попытки трассировки партий.

Если `available < reverseQty` (часть объёма уже ушла в продажу, перемещение, списание или резерв):

- полное сторно отклоняется;
- частичное сторно разрешено на величину `<= available` (§8.8);
- чтобы сторнировать больше — сначала инвентаризация / снятие резерва / возврат продажи, не «форсировать минус».

### 8.8 Частичное сторно

Поддерживается по строкам, в пределах `available` и в пределах ещё не сторнированного qty исходной строки:

```text
получено 100
уже сторнировано 0
available сейчас 90
максимум reversal = min(100 - 0, 90) = 90
```

Связь с исходной строкой поставки обязательна. Сумма всех reversal по строке не может превысить исходный `quantity`.

### 8.9 Границы `documentDate`

`documentDate` задаётся в timezone компании, на сервер уходит как ISO UTC.

Запрещено:

- дата **после конца текущего календарного дня** компании (будущее). Допуск «сегодня» есть, «завтра» — нет;
- дата в **закрытом** учётном периоде без `ACCOUNTING_LATE_ENTRY` и явного подтверждения;
- пустая дата — подставляется текущий день компании.

Рекомендуемое предупреждение (не hard-block): документ старше 365 дней. Hard-block на возраст без late-entry не вводить в MVP, кроме закрытого периода.

## 13. AuditLog

`StockHistory` отвечает за движение товара.

`AuditLog` отвечает на вопрос: **кто и какое административное действие выполнил**.

### 13.1 Модель

```prisma
model AuditLog {
  id          Int      @id @default(autoincrement())
  userId      Int?
  action      String
  entityType  String
  entityId    Int?
  before      Json?
  after       Json?
  reason      String?
  createdAt   DateTime @default(now())
}
```

### 13.2 Обязательные действия для аудита

- проведение поставки;
- отмена DRAFT;
- сторно поставки;
- корректировка остатка;
- проведение инвентаризации;
- списание;
- изменение закупочной цены;
- изменение barcode/SKU;
- утверждение/выплата reward;
- финансовая корректировка;
- **каждый** экспорт accounting (обязательно, не опционально);
- закрытие/открытие периода;
- late entry в закрытый период;
- `PRICE_CHANGE`.

В `before/after` не хранить секреты, токены, пароли.

### 13.3 Retention

`AuditLog` не копится бесконечно без политики.

| Слой | Срок | Действие |
|---|---|---|
| Hot (Postgres) | 24 месяца | Рабочие запросы Control/Audit UI |
| Archive | старше 24 месяцев | Выгрузка JSONL/Parquet в object storage (S3-совместимое). В Postgres остаётся stub: id, userId, action, entityType, entityId, createdAt, archiveUri |
| Legal hold | по запросу суперадмина | Строки не архивируются |

В MVP достаточно:

- индекс по `createdAt`;
- конфиг `AUDIT_RETENTION_MONTHS=24`;
- **no-op job** в том же cron-слое, что и `StagnantProductCronService` (не отдельный worker и не ручной «как вспомним»).

Владелец запуска архивации — пункт **M9 / tech debt**, не скрытый «потом сделаем»:

| Поле | Решение MVP |
|---|---|
| Кто регистрирует job | `server` cron при старте приложения |
| Что делает job | если `AUDIT_ARCHIVE_ENABLED=false` (дефолт) — no-op + log «skipped» |
| Ручной запуск | `POST /api/accounting/audit/archive` только FULL, тоже может быть заглушкой 501 до реализации выгрузки |
| Куда писать archive | не выбирать S3-провайдера в M1; интерфейс `AuditArchiveStorage.put(records)` |
| Когда включать | отдельная задача после M9, когда появится объём |

## 16. Контроль качества данных

Добавить отдельный блок **«Контроль»**.

Минимальный набор:

- продажи без себестоимости;
- продажи с расчётной себестоимостью;
- поставки без `unitCost` для суперадмина;
- оплаты без соответствующей продажи;
- продажи без Payment;
- несогласованные возвраты;
- незавершённые/зависшие DRAFT поставки;
- отрицательные остатки;
- движения без source document;
- подозрительные большие ручные корректировки;
- поставки, не прошедшие сверку;
- расхождение `Revenue + Delivery` против net payments.

### 16.1 Качество COGS

Разделять:

```text
actualCostAmount
estimatedCostAmount
```

Пример:

```text
COGS = 420 000 ₽
auto/estimated = 58 000 ₽
```

UI должен предупреждать пользователя, что часть прибыли рассчитана по оценочной себестоимости.

«Отрицательные остатки» в этом списке — аномалии (§5.6), не плановый режим работы.

### 16.2 Алертинг

Control Center не должен быть единственным каналом. Критичные события дополнительно уходят суперадмину через существующий `Notification` / `UniversalNotificationService`.

Обязательные алерты MVP:

| Событие | Условие |
|---|---|
| Крупная ручная корректировка | `|difference|` или `|qty|` выше порога `ACCOUNTING_ALERT_ADJUSTMENT_QTY` (дефолт 50 коробок) или суммы `ACCOUNTING_ALERT_ADJUSTMENT_AMOUNT` |
| Отрицательный остаток обнаружен | любой `quantity < 0` или `available < 0` после джоба сверки |
| Зависший DRAFT | статус `DRAFT` старше `ACCOUNTING_ALERT_DRAFT_DAYS` (дефолт 3 дня) |
| Late entry | операция в закрытый период |
| Экспорт с cost/profit | факт экспорта FINANCIER/FULL |

Канал MVP: in-app `Notification`. Email — если в проекте уже есть отправка писем. Telegram — V2.

Алерты не подменяют AuditLog: сначала запись в журнал, затем уведомление.

## 17. Периоды и timezone

API принимает ISO UTC.

UI использует timezone компании.

По умолчанию для текущего бизнеса:

```text
Europe/Moscow
```

Но timezone не должен быть жёстко зашит в сервисах. Предусмотреть настройку уровня компании.

Пресеты:

- день;
- неделя;
- месяц;
- год;
- произвольный период.

«Месяц» — календарный месяц, а не «последние 30 дней».

### 17.1 Закрытие периода

Управленческий месяц можно закрыть, чтобы уже сданная отчётность не менялась молча.

```prisma
model AccountingPeriod {
  id         Int      @id @default(autoincrement())
  year       Int
  month      Int      // 1–12, месяц компании, не UTC-календарь сервера
  status     AccountingPeriodStatus @default(OPEN) // OPEN | CLOSED
  closedAt   DateTime?
  closedById Int?
  reopenedAt DateTime?
  reopenedById Int?
  @@unique([year, month])
}
```

Правила:

- по умолчанию период `OPEN`;
- закрывает только `ACCOUNTING_PERIOD_CLOSE` (FULL);
- закрытый период **не** запрещает чтение отчётов;
- write с `documentDate` / датой инвентаризации / датой adjustment, попадающей в закрытый месяц компании:
  - без `ACCOUNTING_LATE_ENTRY` → `403/409` «период закрыт»;
  - с правом и явным `confirmLateEntry=true` → операция проходит, `isLateEntry=true`, AuditLog, алерт, строка в Control Center;
- `soldAt` продаж ставит система при `DELIVERED` текущим временем: закрытие периода не должно ломать операционные продажи «сегодня», если сегодняшний месяц ещё OPEN. Если доставка произошла уже после закрытия того месяца, в который хотели отнести продажу — продажа всё равно пишется сегодняшним `soldAt` (нельзя датировать продажу задним числом);
- повторно открыть период может только FULL, с `reason`, аудитом и алертом.

Продажи и оплаты не переносятся пользователем между периодами. Late entry относится к документам склада: поставки, инвентаризации, списания, сторно, `PRICE_CHANGE`.

Период **глобален на компанию**. В ключе нет `warehouseId`. Закрытие марта закрывает март для всех складов сразу. Закрывать склад А отдельно от склада Б — вне скоупа, не предлагать на ревью как «небольшое расширение».

## 28. Производительность и надёжность

### 28.1 Performance

- summary за месяц по всем складам: p95 < 2 с при рабочем объёме данных;
- реестры — только пагинация;
- обязательные индексы по датам, складам, источникам и статусам;
- тяжёлые summary-кейсы кешируются в Redis на 30–60 секунд.

### 28.2 Transactions

Критические операции:

- receive supply;
- reverse supply;
- inventory completion;
- stock adjustment;
- transfer completion;
- financial adjustment;

выполняются внутри одной транзакции.

### 28.3 Идемпотентность

Критические write-операции принимают заголовок:

```http
Idempotency-Key: <uuid-v4>
```

Обязателен для:

- `POST /api/accounting/supplies/:id/receive`
- `POST /api/accounting/supplies/:id/reverse`
- `POST /api/accounting/supplies/:id/cancel`
- `POST /api/accounting/inventory/:id/complete`
- `POST /api/accounting/transfers/:id/complete`
- финансовых adjustment endpoints, когда появятся

Контракт:

| Повтор | Ответ |
|---|---|
| тот же key, тот же user, тот же request hash, операция уже выполнена | сохранённый ответ (обычно 200/201), **без** второго движения |
| тот же key, другой body | `409` `IDEMPOTENCY_KEY_REUSED` |
| нет key | `400` на перечисленных endpoint |
| документ уже `RECEIVED` / `REVERSED`, другой key | `409` по статусу документа, как и раньше |

Хранение:

```text
IdempotencyRecord(key, userId, endpoint, requestHash, statusCode, responseBody, createdAt)
UNIQUE(key)
TTL 24 часа
```

Платёжные вебхуки ЮKassa — по их event id, отдельно от accounting keys.

### 28.4 Блокировки остатка

См. §5.7 и **§5.7.1**. Без row lock + conditional update write в production не принимается. Любая транзакция с двумя и более `ProductStock` обязана блокировать ключи в порядке `warehouseId, productId` ASC.

## 33. Acceptance criteria

### AC-1 — продажа

Доставлен заказ с 2 позициями → 2 `WarehouseSale`/строки продаж, revenue соответствует историческим ценам продажи. Ручного ввода в accounting нет.

### AC-2 — поставка

Суперадмин проводит 10 коробок на склад A → `ProductStock.quantity += 10`, `StockHistory.SUPPLY`, supply spend увеличивается на `10 × unitCost`.

### AC-3 — повторная поставка

Повторное проведение того же документа → `409` и отсутствие второго прихода.

### AC-4 — доступы

OPERATOR не получает `warehousePrice`, `unitCost`, `costAtSale`, `COGS`, `profit`. FINANCIER получает эти поля, но `receive`/`reverse`/`adjust` → 403. FULL проходит все write.

### AC-5 — reversal

Проведённая поставка не удаляется. Reversal создаёт отдельное движение, связанное с исходным документом.

### AC-6 — частичный возврат

Продано 10, возвращено 2 → net sold = 8; историческая продажа остаётся 10.

### AC-7 — инвентаризация

Ожидалось 100, фактически 95 → создаётся `ADJUSTMENT -5` через InventoryCount.

### AC-8 — цена

Изменение текущего `warehousePrice` не изменяет COGS уже существующих продаж.

### AC-9 — контроль платежей

В отчёте отдельно видны revenue, payments net и difference.

### AC-10 — аудит

Критическое действие создаёт AuditLog с пользователем, сущностью, временем и before/after или причиной.

### AC-11 — источники

Любое движение содержит `sourceType/sourceId` или явную причину для системного события.

### AC-12 — период

Переход через границу месяца/суток в `Europe/Moscow` корректно попадает в календарный период при передаче UTC в API.

### AC-13 — last explicit cost

Две проведённые поставки одного SKU на один склад: 10×80, затем 5×100. Следующая продажа 3 коробки имеет `costAtSale = 100`, `isEstimatedCost = false`. Первая продажа, если была между поставками, сохраняет 80.

### AC-14 — пустой unitCost

Проведение строки без `unitCost` не меняет существующий `warehousePrice` и не пишет `null` поверх явной цены.

### AC-15 — сторно без партий

На остатке 4 доступных из прихода 10. Полное сторно 10 → отказ. Частичное сторно 4 → успех. Остаток не отрицательный.

### AC-16 — запрет минуса

`decrementAvailable` / продажа / write-off при нехватке available не создают движение и не создают `WarehouseSale`.

### AC-17 — идемпотентность

Два параллельных POST receive с одним `Idempotency-Key` → один приход, второй ответ копия первого.

### AC-18 — закрытый период

После закрытия марта проведение поставки с `documentDate` в марте без late entry → отказ. С `confirmLateEntry=true` у FULL → успех, `isLateEntry=true`, алерт.

### AC-19 — независимые возвраты

`ProductReturn` COMPLETED увеличивает склад и пишет `SalesAdjustment` при связи с продажей, но не меняет `Payment`. Refund Payment не пишет `StockHistory`.

### AC-20 — экспорт

Успешный export с cost-полями пишет AuditLog. OPERATOR-export не содержит cost/profit колонок. 11-й export за 10 минут → 429.

### AC-21 — порядок блокировок

Два параллельных complete transfer: склад 1→2 и склад 2→1 по одному SKU. Оба завершаются без deadlock (или один ретраится по 40P01 и доходит с тем же Idempotency-Key). Остатки согласованы: сумма по двум складам не изменилась.

## 34. Риски и mitigation

| Риск | Mitigation |
|---|---|
| Float в старых моделях | Новые деньги только Decimal; старые данные конвертировать в Decimal на границе расчёта. |
| Нет исторического COGS | Хранить `costAtSale`; не читать текущий `ProductStock.warehousePrice`. |
| Возврат после DELIVERED | Отдельный adjustment/reversal, не удалять продажу. |
| Отмена проведённой поставки | Только reversal event, не физическое удаление. |
| Частичный возврат поставщику | Отдельная reversal/supply-return операция. |
| Ошибка пользователя при корректировке | AuditLog + обязательная reason. |
| Тяжёлые агрегаты | Индексы + Redis cache. |
| Смешение UTC/local | API UTC + company timezone в UI. |
| Неполная себестоимость | estimated vs actual cost + Control Center. |
| Исторический KPI меняется | использовать assignment snapshot; если отсутствует — явно документировать ограничение. |
| Несогласованная старая Supply | Сначала inventory/count; затем миграция или adapter. |
| Barcode duplicate | DB unique constraint + backend validation. |
| Прямая запись ProductStock | Запретить из accounting; только `InventoryService`. |
| Неясный last-cost | Алгоритм §5.5: пустой unitCost не трогает цену; явный unitCost затирает last explicit. |
| Сторно «этой» поставки без партий | Только проверка `available`; зафиксировано в §8.7. |
| Отрицательный остаток | Запрещён на всех write-path; Control — детектор бага. |
| Гонки на стоке | FOR UPDATE + version + conditional updateMany, §5.7. |
| Правка закрытого месяца | AccountingPeriod + late entry, §17.1. |
| Двойной клик receive | Обязательный Idempotency-Key, §28.3. |
| Refund 1:1 с товаром | Запрещено связывать автоматически, §5.8. |

## 35. Миграция старой Supply

Перед миграцией проверить:

```text
SELECT COUNT(*) FROM Supply
```

и использование в коде.

Если боевые строки отсутствуют:

- внедрить новую `SupplyDocument`;
- старую модель оставить deprecated на переходный период;
- удалить только после проверки зависимостей и миграции.

Если строки существуют:

- создать адаптер;
- сохранить исторические данные;
- не удалять старые записи;
- новые операции вести только через `SupplyDocument`.

## 38. Финальная модель данных

Логически accounting строится вокруг следующих объектов:

```text
Product
  ├─ barcode / SKU
  │
  ├─ ProductStock
  │
  ├─ WarehouseSale
  │      └─ SalesAdjustment
  │
  ├─ SupplyDocument
  │      └─ SupplyDocumentLine
  │            └─ SupplyReversal
  │
  ├─ InventoryCount
  │      └─ InventoryCountLine
  │
  └─ StockHistory

Payment
EmployeeReward
Driver
Stop
Employee
AuditLog
AccountingPeriod
IdempotencyRecord
```

На `ProductStock` в этом релизе добавить `version Int @default(0)` для optimistic lock (§5.7). На документах склада — `isLateEntry Boolean`.

Все финансовые отчёты являются проекциями этих первичных данных, а не отдельной независимой системой проводок.

## 39. Принципы, которые нельзя нарушать

1. **Accounting не создаёт продажи вручную.**
2. **Нельзя удалять проведённые хозяйственные операции.**
3. **Исправление истории выполняется новой корректирующей операцией.**
4. **Историческая себестоимость продажи не пересчитывается текущей ценой остатка.**
5. **Нельзя обходить InventoryService прямыми изменениями ProductStock.**
6. **Нельзя отдавать закупочные цены и прибыль через API ролям без `ACCOUNTING_COST_VIEW` / `ACCOUNTING_PROFIT_VIEW`.**
7. **Каждое движение должно иметь источник или объяснимую причину.**
8. **Все критические действия должны быть аудируемыми.**
9. **Закупки не должны второй раз попадать в COGS.**
10. **Расхождения не скрываются и не подгоняются.**
11. **Неполная себестоимость должна быть видима как estimated.**
12. **Денежные расчёты новых моделей выполняются в Decimal.**
13. **Период отчётности определяется timezone компании, а API работает с UTC.**
14. **Исторические показатели KPI не должны зависеть от случайного изменения текущих связей.**
15. **Отрицательный остаток запрещён; SELL и reversal не уходят в минус.**
16. **Себестоимость MVP = last explicit cost на остатке + иммутабельный снимок в продаже; пустой unitCost цену не затирает.**
17. **Сторно поставки проверяет только available, без претензии на партионную трассировку.**
18. **Товарный возврат и денежный refund независимы.**
19. **Мутации остатка — только с блокировкой строки ProductStock.**
20. **Закрытый период не правится молча; late entry видим в аудите и контроле.**
21. **Критические write требуют Idempotency-Key.**
22. **Permission глобален, складской scope — отдельный слой.**
23. **Несколько ProductStock в одной транзакции блокируются только в порядке `(warehouseId, productId)` ASC.**
24. **`SUPPLY_RETURN` в MVP не пишется; возврат поставщику — V2.**
25. **EMPLOYEE инвентаризирует свои склады по умолчанию, без отдельной выдачи права.**
26. **Учётный период один на компанию, не на склад.**

## 40. Итог

После реализации модуль должен давать суперадмину единую, воспроизводимую картину:

```text
ОПЕРАЦИИ
   ↓
Продажи / Поставки / Возвраты / Оплаты / Инвентаризация / Списания
   ↓
Первичные документы + StockHistory + AuditLog
   ↓
Accounting API
   ↓
┌─────────────────────────────────────────┐
│ Продажи │ COGS │ Прибыль │ Деньги       │
│ Склады  │ KPI  │ Контроль│ Поставки     │
└─────────────────────────────────────────┘
```

Цель MVP — не построить 1С, а сделать так, чтобы в Iceberg **любая существенная цифра имела источник, историю, пользователя и объяснимый путь формирования**.

После внедрения текущий ручной ввод должен постепенно свестись к трём контролируемым типам действий:

1. создание/проведение первичных документов;
2. фактическая инвентаризация;
3. корректирующие операции с причиной и аудитом.

Продажи, остатки, движения и финансовые агрегаты должны формироваться автоматически из этих событий.
