# Управление заказами в веб-панели админа

План экранов `/orders` и `/orders/:id` для `User.role === 'ADMIN'`.

Мобильное приложение сотрудников и корневой `tasks.md` (весовые заказы) не меняем. Поставщик и сотрудник в вебе этот раздел не видят: сборщик и курьер остаются в мобильном приложении.

**Архитектура: FSD**, как у пользователей и возвратов. Страницы не вызывают axios напрямую. Публичный API — `entities/order` и `features/order-admin`. Стек страниц: Ant Design, React Query, `RoleGate`. Новые npm-зависимости не добавляем: живое обновление — повторный запрос списка, не Socket.IO.

Каждая фаза оставляет `npm run build` (`tsc -b && vite build`) зелёным.

---

## 1. Что уже есть и что строим поверх

Сервер уже проводит заказ по графу из `server/src/services/orders/orderLifecycle.js`. Веб только вызывает эти ручки и показывает то, что мобильный сотрудник видит в `OrderDetailsEmployeeScreen`.

```text
AWAITING_CONFIRMATION → PENDING_PAYMENT   подтверждение цены (весовой заказ)
PENDING_PAYMENT       → PENDING           оплата клиента (веб оплату не проводит)
PENDING / CONFIRMED   → PICKING           очередь сборки после оплаты (cron / autoAssign)
PICKING               → IN_DELIVERY       скан сборки, затем передача в доставку
IN_DELIVERY           → DELIVERED         курьер или админ
любой рабочий         → CANCELLED         причина от 10 символов, возврат стока/резерва
DELIVERED             → RETURNED          только этот переход после выдачи
```

Сборка, доставка и «доставлен» без captured-оплаты запрещены (`orderPaymentGate`). Переход в `IN_DELIVERY` без `pickingVerifiedAt` запрещён (`orderPickingGate`). Из `AWAITING_CONFIRMATION` в `PENDING_PAYMENT` нельзя прыгнуть сменой статуса — только `PATCH /api/orders/:id/confirm-price`.

Админ в `staffClientPrivacy` уже получает полное имя, телефон и адрес. Сборщик их не видит; курьер — только на своём заказе в `IN_DELIVERY`.

### Ручки, которые панель вызывает как есть

| Действие админа | Метод | Заметка |
|---|---|---|
| Список всех заказов | `GET /api/orders` | Для `ADMIN` склад не режется |
| Карточка | `GET /api/orders/:id` | Клиент, позиции, оплата, склад, исполнитель, история статусов, токен сборки |
| Смена статуса | `PATCH /api/orders/:id/status` | Только разрешённый переход + оплата + скан |
| Подтвердить сборку | `POST /api/orders/:id/picking/scan` | Тело `{ token }`, токен уже есть в карточке админа |
| Назначить / снять | `PATCH /api/orders/:id/assign` | `{ assignedToId, reason }`, `assignedToId: null` снимает |
| Подтвердить цену рыбы | `PATCH /api/orders/:id/confirm-price` | `ADMIN` уже проходит `requirePriceConfirmer` |
| Отмена | `PATCH /api/orders/:id/cancel` | `{ reason }` 10–500 символов |
| Накладная | `GET /api/orders/:id/invoice` | PDF |
| Чек | `GET /api/payments/orders/:orderId/receipt` | Карточка оплаты |
| Счётчики | `GET /api/orders/stats` | Виджет на кабинете |
| Сотрудники склада | `GET /api/employees/all` | Список для назначения |
| Загруженность | `GET /api/orders/warehouses/:warehouseId/workload` | Подсказка в модалке назначения |

`GET /api/orders` для админа не прячет заказы по роли сборщика/курьера. Обычный `PENDING_PAYMENT` (не рыба) из списка персонала скрыт: его видит только клиент, пока не оплатит. Весовой `PENDING_PAYMENT` виден — цена уже подтверждена, ждём оплату.

Движение по сотрудникам уже пишется в `OrderStatusHistory.comment`: назначение, снятие и завершение этапа дописывают текст и маркер `[employee_id:N]`. Отдельной таблицы назначений нет. Текущий исполнитель — `assignedTo`. Кто подтвердил цену — `priceConfirmedBy`.

## 2. Дыры, без которых админская панель врёт

Их закрываем в фазе 0, до вёрстки. Мобильный контракт не ломаем.

1. **Админ не может завершить этап.** `completeOrderStage` в контроллере требует строку `Employee` и `assignedToId === employee.id`. У админа сотрудника нет, поэтому «собрал / передал / доставил» с веба через эту ручку сейчас 403. Сервис уже умеет виртуального админа (`processingRole: 'ADMIN'` → следующий статус по `nextStatusForStage`), но контроллер до сервиса не доходит.
2. **Поиск не применяется.** Joi принимает `search`, `buildOrderWhereClause` его игнорирует.
3. **Фильтр дат не доходит до сервиса.** Схема ждёт `startDate` / `endDate`, сервис читает `dateFrom` / `dateTo`, контроллер не передаёт ни то ни другое.
4. **Фильтр исполнителя не работает.** Контроллер кладёт `assignedToId`, сервис смотрит `assignedToMe`.
5. **В карточке нет журнала действий и предложений клиенту.** `getOrderById` не подгружает `orderLogs` и `clientChoices`. История статусов есть, но без автора, если смена статуса прошла через `updateOrderStatus` (комментарий «Статус изменен с X на Y» без имени).

Оплату, скан сборки и граф статусов не обходим. Админ подтверждает сборку тем же `picking/scan`, затем переводит статус.

## 3. Экраны

### Список `/orders`

Вкладки очереди (счётчик на вкладке):

| Вкладка | `status` |
|---|---|
| Взвешивание | `AWAITING_CONFIRMATION` |
| Ждут оплату | `PENDING_PAYMENT` |
| Сборка | `PICKING` |
| В доставке | `IN_DELIVERY` |
| Ждут товар | `WAITING_STOCK` |
| Доставлены | `DELIVERED` |
| Отменены | `CANCELLED` |
| Все | без status |

Фильтры: склад, период, срочные, поиск (номер заказа, имя или телефон клиента), «назначен на». Пагинация серверная, `limit` 20.

Колонки: номер, статус, срочный / весовой, клиент и район, склад, исполнитель, сумма, оплата (`payment.status` + `paidAt`), дата, действие «Открыть».

Пустой список, ошибка с текстом API, горизонтальный скролл на узком экране — как у возвратов.

### Карточка `/orders/:id`

Шапка: номер, бейдж статуса, срочность, склад, тип доставки.

Блоки:

- **Клиент.** Имя, телефон, email, район, полный адрес, комментарий. Для админа сервер маску не ставит.
- **Состав.** Название, количество, цена, сумма строки. Весовая строка: ориентир `estimatedWeightKg` / `estimatedPrice`, факт `actualWeightKg × pricePerKg`.
- **Деньги.** Товары, доставка, итог, `estimatedAmount`, если цена ещё не подтверждена. Оплата: статус, сумма, `paidAt`, способ, маска карты, id банка, ссылка на чек.
- **Исполнитель.** Кто назначен сейчас (имя, роль обработки). Кнопки «Назначить» и «Снять».
- **История.** `statusHistory` снизу вверх по времени: статус, комментарий без маркера `[employee_id:…]`, сотрудник из маркера или из текста «Обработано сотрудником …». Отдельным шагом: кто подтвердил цену, когда сборка подтверждена (`pickingVerifiedAt`). Ниже — `orderLogs` (действие, пользователь, время), если они есть.
- **Ожидание товара.** `waitingDeadline`, если статус `WAITING_STOCK`. Включение заказа остаётся за cron, кнопка «активировать» не нужна.
- **Предложение клиенту.** Если есть `clientChoices` — тип, статус, срок. Мастер замен в этой задаче не делаем.

Действия зависят от статуса (кнопка есть только если переход разрешён графом и гейтами):

| Статус | Кнопки |
|---|---|
| `AWAITING_CONFIRMATION` | Форма взвешивания: факт. вес, цена за кг, «убрать позицию», доставка, комментарий → `confirm-price` |
| `PENDING_PAYMENT` | Только текст «Ждём оплату клиента». В сборку не переводим |
| `PICKING` (и `PENDING` / `CONFIRMED` / `PACKING`, если такие ещё висят) | «Подтвердить сборку» (`picking/scan` с `pickingToken`), после `pickingVerifiedAt` — «Передать в доставку» |
| `IN_DELIVERY` | «Доставлен» |
| рабочие статусы из `STAFF_CANCELLABLE` | «Отменить» с причиной |
| `DELIVERED` | «Возврат» → `RETURNED`, плюс скачать накладную |

«Передать в доставку» и «Доставлен» идут через `complete-stage` после фазы 0, чтобы в истории было «Обработано администратором», а исполнитель сбрасывался так же, как у менеджера в мобилке. Пока фаза 0 не влита, эти две кнопки не включаем: голый `PATCH status` историю сотрудника не пишет.

Накладная доступна на любом статусе, где ручка отдаёт PDF.

После любого действия карточка и список перезапрашиваются.

### Кабинет админа

На `DashboardPage` для `ADMIN` — четыре счётчика со ссылками: взвешивание, сборка, в доставке, ждут товар. Кабинет поставщика не трогаем.

### Фаза 8. Не входит в этот заход

- Оформление заказа за клиента (`POST /api/orders/create`, касса). Отдельная задача: склад, позиции, адрес.
- Мастер замен и дробления (`orderAlternatives`). На карточке только показ уже созданного `clientChoices`.
- Экспорт `POST /api/orders/export` и массовый `PATCH /api/orders/bulk`.
- Раздел заказов для `EMPLOYEE` в вебе.
- Обход скана сборки и оплаты, правка цены после `PENDING_PAYMENT`, ручная активация `WAITING_STOCK`.
- Socket.IO в вебе. Список обновляется раз в 30 секунд и сразу после своего действия.

## 5. Как проверять

- `cd web && npm run build` после каждой фазы.
- Фаза 0: точечно дернуть `complete-stage`, `GET /api/orders?search=`, фильтр склада и дат под админом и убедиться, что мобильный сборщик всё ещё не закрывает чужой заказ.
- Фазы 4–7: в браузере под админом пройти список, карточку, взвешивание, скан, передачу в доставку, назначение, отмену. Под поставщиком меню «Заказы» нет.
